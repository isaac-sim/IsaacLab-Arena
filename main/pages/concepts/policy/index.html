Policy#

A policy in Arena is a standard interface between your model and the evaluation pipeline. You implement one method — get_action(env, obs) — and the policy plugs into both the single-job runner and the Experiment Runner without any changes to either. In bare IsaacLab you would write an ad-hoc inference loop for each model; Arena’s PolicyBase gives a consistent contract that all runners depend on.

policy = ZeroActionPolicy(config=ZeroActionPolicyCfg())
obs, _ = env.reset()
action = policy.get_action(env, obs)

Built-in policies#

Arena ships with four policies:

ZeroActionPolicy ("zero_action")

Returns a zero-filled action tensor. Useful for validating an environment without a trained model.

ReplayActionPolicy ("replay")

Replays actions from a recorded episode stored in an HDF5 file.

RslRlActionPolicy ("rsl_rl")

Runs inference with a trained RSL-RL checkpoint. Loads the checkpoint and its accompanying params/agent.yaml automatically.

Writing a custom policy#

Define a typed PolicyCfg, subclass PolicyBase with that config, set a name, register it with its config, and implement get_action:

from dataclasses import dataclass

import gymnasium as gym
import torch
from gymnasium.spaces.dict import Dict as GymSpacesDict

from isaaclab_arena.assets.register import register_policy
from isaaclab_arena.policy.policy_base import PolicyBase, PolicyCfg


@dataclass
class MyPolicyCfg(PolicyCfg):
    device: str = "cuda:0"


@register_policy
class MyPolicy(PolicyBase[MyPolicyCfg]):
    name = "my_policy"

    def __init__(self, config: MyPolicyCfg):
        super().__init__(config)

    def get_action(self, env: gym.Env, observation: GymSpacesDict) -> torch.Tensor:
        # Your model inference here
        return torch.zeros(env.action_space.shape, device=torch.device(env.unwrapped.device))

Construct the policy by passing its typed configuration directly:

policy_cfg = MyPolicyCfg(device="cuda:0")
policy = MyPolicy(policy_cfg)

The typed registration lets the single-job runner generate CLI flags from MyPolicyCfg and lets the Experiment Runner convert the current Job.policy_config_dict representation into that same type. See Arena Experiments for details.

Config fields named device or num_envs reuse the corresponding shared runner flags, so their defaults must match the runner defaults.

Note

policy_runner.py remains an argparse frontend, but policies do not implement argparse methods. The runner generates their flags from the registered config and reconstructs it before creating the policy.

VLM agent policies#

VLMGoalPolicy and VLMChunkPolicy in the isaaclab_arena_vlm_agent package use a hosted vision-language model as the policy. At each request, the policy sends the task, the robot state, and the camera images to an OpenAI-compatible endpoint, then validates the JSON command it returns and executes it. VLM Agent shows how to set up an endpoint and run them on DROID pick-and-place.

Inference and execution flow#

Each request runs through these stages:

observation ─► observation adapter ─► images + JSON state ─┐
                                                           ├─► inference backend ─► JSON response
embodiment preset ─► system prompt + response schema ──────┘                             │
                                                                                         ▼
robot action ◄─ motion generator (goal only) ◄─ action adapter: validate + decode ◄──────┘

The paragraphs below follow the diagram. Each one links to the code that implements the stage for DROID.

System prompt, from the embodiment preset. DroidVLMAdapter in droid_adapter.py writes the system prompt. It also creates the action adapter and, for the goal policy, the motion generator. The DROID prompt states:

  • the pose and gripper command layout and the coordinate frames;

  • how to use the camera calibration;

  • for the goal policy and step mode, that base_link sits 0.131 m behind the point between the finger pads;

  • for the goal policy, what the previous-goal outcomes mean;

  • for step mode, how to grasp and keep holding.

Set policy.system_prompt to replace it.

Request, from the observation adapter. The adapters in observation_adapter.py pick the images and state to send. VLMPolicy._request_content in vlm_agent_policy.py encodes the images and builds the user message. It contains:

  • the task text, plus the previous goal and its outcome for the goal policy;

  • the policy observations, such as end-effector pose, gripper position, and the last action;

  • the pose of the commanded body in the robot root frame;

  • for each camera, the image size, intrinsics, and optical-frame pose in the world and robot root frames;

  • the RGB images as JPEG, resized so their longer side is image_max_width_or_height pixels (384 by default).

observation_modality selects the content: image, state, or image_state (the default).

Inference backend. InferenceBackend in backend.py sends the system prompt, the user message, and the response schema to the endpoint. It retries failed HTTP requests and responses that are not valid JSON.

Response, from the action adapter. AbsoluteChunkActionAdapter and AbsoluteGoalActionAdapter in absolute_action_adapter.py define a strict JSON schema:

  • goal: {"values": [...]}

  • chunk: {"commands": [{"values": [...]}, ...]}

The adapter rejects a response with the wrong number of values, non-finite values, a quaternion that is not unit length, or a gripper value other than open or closed. It sends the error back to the model and asks for a corrected response, up to max_attempts times.

Execution, by the motion generator (goal policy only). PoseTargetMotionGenerator in pose_target_motion_generator.py holds the goal pose, closes or opens the gripper, and reports the goal as:

  • reached: within position_tolerance_m and rotation_tolerance_rad, with the gripper at its target or stopped while closing on an object;

  • blocked: the arm and fingers stopped moving short of the goal for several steps.

Add your own implementation#

Every stage except the inference backend is a part you can replace without touching the others. The rows follow the order of the stages above.

Pipeline stage

Part

What to implement

System prompt

Embodiment preset

A class with make_chunk_action_adapter(chunk_size), make_goal_action_adapter(position_tolerance_m, rotation_tolerance_rad), and get_system_prompt(action_adapter). It ties the other parts to one robot and writes the prompt. DroidVLMAdapter is the reference.

Request

Observation adapter

Subclass VLMObservationAdapter and implement extract_vlm_input_from_observation(env, observation, env_id). It returns the images by camera name and the JSON-serializable values to send.

Response

Action adapter

Subclass ChunkActionAdapter or GoalActionAdapter. Set response_model, a Pydantic model that defines the response schema. Implement is_robot_action_space_supported(env) to check the robot’s action terms, and decode_command(response, arena_world, env_id) to convert a response into native commands. Raise InvalidAgentResponseError to ask the model for a correction.

Execution (goal policy only)

Motion generator

Subclass MotionGenerator and implement compute_command(goal, env, env_id) and goal_reached(goal, env, env_id). Optionally implement goal_blocked to report stalls.

Support a new robot. AbsoluteChunkActionAdapter and AbsoluteGoalActionAdapter read the command layout from the robot’s active action terms and pass the model’s values to them unchanged. You can reuse them if every action term is one of these:

  • DifferentialInverseKinematicsAction with command_type="pose", absolute mode (use_relative_mode=False), scale 1, and no body_offset. It takes seven values: XYZ and an XYZW quaternion.

  • JointPositionAction with scale 1, offset 0, and use_default_offset=False.

  • BinaryJointPositionAction or BinaryJointPositionZeroToOneAction with one value.

No term may set clip. If any term does not match, is_robot_action_space_supported returns False and the policy stops with an assertion error before its first request. command_indices.py implements these checks. For other controllers, write your own action adapter.

Next, write a preset that describes the layout and the frames in its prompt. In isaaclab_arena_vlm_agent/vlm_agent_policy.py, add the preset name where VLMPolicyCfg validates vlm_embodiment_adapter and where _get_vlm_embodiment_adapter creates the preset. Then select it in the YAML:

policy:
  type: isaaclab_arena_vlm_agent.vlm_agent_policy.VLMGoalPolicy
  vlm_embodiment_adapter: my_robot
  max_steps_per_goal: 30

Add an execution strategy. Subclass VLMPolicy with its own typed configuration and register it with @register_policy, as in Writing a custom policy. Then implement two methods:

  • _get_command(env, observation, env_id): decide when to request a new prediction, and call self._infer(self._request_content(...), ...) to get a validated one.

  • reset(env_ids): discard pending predictions.

VLMPolicy already handles request assembly, image encoding, response validation, and the correction loop.
