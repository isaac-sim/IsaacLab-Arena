# Branch changes: `yaml-env-experiment-config`

- **Graph-spec YAML environments end-to-end** — `environment.type` in a typed YAML experiment can name a graph-spec YAML (e.g. `robolab/tasks/*.yaml`); such runs build through the legacy graph-env path with the typed `environment_builder` (so post-load Hydra overrides like `num_envs` apply) and round-trip through OSMO submission (the serializer records and re-emits each graph run's spec path and values).
- **Per-run policy-server derivation in the OSMO Arena-experiment workflow** — the co-scheduled inference server for each Run is derived from its client policy (pi0 or GR00T) via a registry, so one experiment can mix policy types and each Run gets the right server. `--policy_server` is removed; per-server-type deployment config moves to `servers.<name>.*`, and all servers in one submission must share a pool. (The GR00T `scheduler` config annotation was relaxed so it composes under Hydra.)
- **`submit_arena_experiment.py` CLI flags** — `--dry_run` (render the workflow YAML without submitting) and `--list_overrides` (print the composed submission, i.e. the Hydra override namespace).
- **OSMO docs** — added a "Running Large-scale Evaluations on OSMO" page under Example Workflows.
- **robolab example experiment configs** — `robolab_4_tasks.yaml` / `.json` (and `robolab_2_tasks.yaml`) running the robolab graph environments.
- **OSMO experiment-runner records video** — `ExperimentRunnerTaskCfg` gains `record_camera_video` (default True) / `record_viewport_video`, and the task now passes those flags (it recorded nothing before).
- **Directional light in graph environments** — the graph converter (`_ensure_scene_lighting`) injects a `directional_light` alongside the dome, so graph/robolab scenes support `directional_light.direction`/`.intensity` lighting variations.
- **pi0+GR00T robolab configs** — `robolab_2_tasks_pi0_and_gr00t.yaml` and `robolab_20_tasks_pi0_and_gr00t.yaml` run each task under both policies (per-policy `num_envs`).
- **Stall-restart watchdog for OSMO Runs** — `experiment_runner_watchdog.py` wraps `experiment_runner.py` as a subprocess; if the runner emits no output for `watchdog_stall_timeout_seconds` (default 600s) it kills the process group, clears the Run's output directory, and relaunches, up to `watchdog_max_restarts` (default 5). Each OSMO Run's `ExperimentRunnerTask` invokes the runner through it. Stop-gap for individual Runs hanging and killing the whole distributed Experiment; the real fix is finding why runs stall.
- **Distinct seed per rebuild** — `build_and_run` now offsets the environment-builder seed by the rebuild index (`seed + rebuild_index`), so each of a Run's `num_rebuilds` fresh constructions draws its own build-time variations. Previously every rebuild reused the same seed, so a build-time variation (e.g. `directional_light.direction`) resolved to the same value on every rebuild (verified: rebuilds 1..N were identical). Rebuild 0 is unchanged, so single-rebuild runs are unaffected.
- **Disable HDF5 file locking in OSMO Runs** — the `ExperimentRunnerTask` run script exports `HDF5_USE_FILE_LOCKING=FALSE` before the watchdog command. Each Run writes its own single-writer episode dataset, so the lock buys nothing, and a stalled process the watchdog kills can leave the lock held on the cluster filesystem — making the relaunched Run die creating its dataset (`BlockingIOError`, errno 11). Observed as a watchdog restart succeeding into an immediate HDF5-lock failure; disabling the lock turns those stalls into successful auto-recoveries.
- **Cosmos policy in the OSMO Arena-experiment workflow** — a new `CosmosServerTask` (serves the `cosmos_server` image via `cosmos_framework.scripts.action_policy_server_robolab`) plus a `cosmos` `ServerBinding`, so a Run whose policy is `CosmosRemotePolicyCfg` co-schedules a Cosmos server like pi0/GR00T do. `servers.cosmos.*` exposes the deployment config; `robolab_2_tasks_cosmos.yaml` is a runnable template. The gated `nvidia/Cosmos3-Edge-Policy-DROID` checkpoint is baked into the image at build time (`build_server_image.sh` downloads it via a BuildKit secret to `/workspace/baked_checkpoint`), so the running server — and the OSMO task — need no `HF_TOKEN`, matching how GR00T ships its checkpoint in the image.
